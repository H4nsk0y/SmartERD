# SmartERD

SmartERD — прототип веб‑приложения для визуального проектирования ER‑диаграмм и получения исполнимых DDL‑скриптов (SQL). Проект выполнен в рамках выпускной квалификационной работы и ориентирован на учебные и первые практические сценарии, где критичны прозрачность преобразования, контроль ошибок и воспроизводимая проверка результата.

## Назначение

Цель SmartERD — снизить трудоемкость и количество типовых ошибок при переходе от концептуальной ER‑модели к реляционной схеме и DDL за счет единого рабочего процесса: построение модели в редакторе → формальная проверка → рекомендации по улучшению структуры → генерация SQL. AI‑компонент используется как вспомогательный: он формирует черновую ER‑модель по текстовому описанию и помогает в справочных запросах, после чего результат доводится средствами валидации и нормализации.

## Состав решения

Репозиторий содержит следующие основные части:

- `frontend/` — клиентская часть (React + TypeScript + Vite), визуальный редактор, генератор SQL на клиенте, модуль валидации/нормализации, тесты и бенчмарки.
- `backend/` — серверная часть (Node.js/Express), API, Prisma‑схема и миграции, интеграционные тесты.
- `ddl-check/` — инфраструктура кросс‑диалектной проверки исполнимости DDL: сценарии, скрипты и логи.
- `docker-compose.yml` — запуск базовой инфраструктуры проекта.
- `docker-compose.ddlcheck.yml` — окружения СУБД для DDL‑верификации.

## Кросс‑диалектная верификация исполнимости DDL

Подсистема `ddl-check` предназначена для воспроизводимого подтверждения практической пригодности генерируемого DDL: для каждого сценария формируется SQL‑скрипт, он выполняется в изолированном окружении целевой СУБД, а результат сохраняется в логах. Это позволяет повторять прогон и трассировать причины ошибок до конкретного сценария и диалекта.

- Скрипты для диалектов: `ddl-check/scripts/`
- Набор сценариев (JSON‑модели): `ddl-check/test-cases_json/`
- Логи выполнения: `ddl-check/logs/`

## Требования к окружению

Для сборки и запуска требуется наличие:
- Node.js и npm (для `frontend` и `backend`);
- Docker и Docker Compose (для инфраструктуры и `ddl-check`);
- LM Studio (опционально, если используется AI‑режим).

## Конфигурация (переменные окружения)

Конкретный набор переменных зависит от текущей конфигурации проекта. Как правило:
- Frontend использует адрес backend API (например, через `VITE_API_URL`).
- Backend использует параметры подключения к БД (Prisma) и параметры AI‑интеграции (base URL OpenAI‑совместимого сервиса и имя модели).

Рекомендуется ориентироваться на файлы конфигурации и код:
- `frontend/src/api/*`
- `backend/src/server.js`
- `backend/prisma/schema.prisma`

## Запуск (локальная разработка)

### Frontend

В `frontend/package.json` определены актуальные сценарии сборки/запуска:

```bash
cd frontend
npm ci
npm run dev
```

Сборка и проверка:

```bash
npm run build
npm run lint
npm run test
```

### Backend

Команды запуска backend определяются в `backend/package.json`. Для разработки обычно используются сценарии из раздела `scripts`. При необходимости можно ориентироваться на входной файл `backend/src/server.js`.

## Тестирование

### Frontend (точные команды)

```bash
cd frontend

# unit
npm run test
npm run test:run
npm run coverage

# BDD (cucumber)
npm run bdd
npm run bdd:fast
npm run bdd:load

# E2E (Playwright)
npm run e2e
npm run e2e:report

# mutation testing (Stryker)
npm run mutate

# micro-benchmarks и генерация графиков
npm run bench
npm run report:plots
```

### Backend

В backend присутствуют unit‑тесты и интеграционные тесты (`src/tests/integration/`), а также конфигурации Vitest:
- `vitest.config.js`
- `vitest.integration.config.js`

Способ запуска тестов задается `backend/package.json` (раздел `scripts`).

## DDL-check: запуск прогона

```bash
docker compose -f docker-compose.ddlcheck.yml up -d
bash ddl-check/run_ddl_check.sh
```
